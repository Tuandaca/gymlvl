# P10.3b — Local placement persistence and consumer contract

**Status:** ACCEPTED for local/test implementation under D-062 on 2026-11-13 by “Phê duyệt D-062 cho local/test”. D-060 numeric policy is also approved locally. Production migration/activation is unapproved.
**Inputs:** D-060; `P10_3A_PLACEMENT_THRESHOLDS_V0_1.md`; `docs/audit/P10_3B_LEVEL_CONSUMERS.md`.
**Authorization granted by D-062:** Additive local/test SQL + Flutter implementation of this contract. Production migration, rollout, Git publication and demographic telemetry collection remain separate gates.

## 1. Earned and readiness values

Existing `users.level`, `users.total_xp`, `users.current_level_xp`, `user_classes.level/current_xp/is_graduated`, and P9 `class_level_floors` keep their current earned/legacy meanings. Current reward, achievement, unlock, graduation, quest and switch-class functions keep consuming those values.

Placement exposes separate fields: `policyVersion`, `status`, `assessedClassId`, `provisionalClassLevel`, `provisionalGlobalLevel`, `confirmedClassFloor`, `confirmedGlobalFloor`, `readinessClassLevel`, `readinessGlobalLevel`, `readinessXpToNextGlobalLevel`, and `readinessXpToNextClassLevel`. The last four are server-calculated, labelled readiness values. They are never substituted into an earned `level` key. Provisional values are estimates for plan choice; confirmed values use server-recorded workout evidence, which does not prove physical technique or honesty.

B/F labels always say training readiness. Dashboard/progression may display readiness separately from earned RPG progression. Existing XP badges, title, unlock list, workout receipt and level-up animation continue using earned values. Readiness alone grants no XP, PR, quest, streak, achievement, unlock or graduation, including after later unrelated workouts.

## 2. Additive storage

All three tables reference `public.users(id) ON DELETE CASCADE`, enable RLS and revoke direct client writes. Owner-only SELECT policies expose the owner's records; no anonymous SELECT or client INSERT/UPDATE/DELETE. Helper functions and administrative aggregates have no authenticated EXECUTE grant. Account-deletion regression must verify the existing P8 user deletion cascades through the new graph.

| Proposed table | Identity / fields | Invariant |
|---|---|---|
| `placement_assessments` | UUID `id`, `user_id`, UUID `operation_id`, immutable `policy_version`, assessed primary class, server timestamps, `status`, normalized request and immutable submission-result JSONB, age/body-mass/timezone snapshots, anchor inputs, provisional scores/reason, `is_initial_enrollment`, optional reference to that first row, immutable initial `has_training_experience`, allowlisted `recommended_plan_route`. Unique `(user_id, operation_id)` and one initial-enrollment row per user. | Only first new onboarding creates enrollment. At most one pending assessment per user; old account rows are not backfilled. Exact retries return their first submission result even after status changes; reused operation ID with different normalized request is rejected. No raw health-reason text or gender telemetry. |
| `placement_workout_evidence` | `(assessment_id, workout_id)` primary key, `user_id`, server-recorded completion time/local date, assessed class, `phase` (`evidence` or `progress`), qualification/rejection reason, per-anchor scores/class score when qualifying, post-confirmation global/class XP deltas when `phase=progress`, policy version. Canonical exercise UUIDs are resolved from the seven curated slugs and checked against catalogue ownership/provenance. MIT source-prefixed exercises, custom definitions and alternate variants do not alias an anchor. Store exactly the validated variant/protocol and reject duplicate exercise IDs, extra metrics, nonfinite values and conflicting bodyweight/load units.

The immutable assessment body-mass snapshot is the ratio denominator for its pending evidence; editing `profiles.weight_kg` never changes an earlier calculation. If a user wants to use a changed body mass before confirmation, a new explicit assessment supersedes the pending one and its evidence cannot be reused. No profile update silently resets placement or earned history.

## 3. RPC and transaction boundaries

Request envelope: `p_profile.placement = {operationId: <uuid>, request: <object>}`. The request object has allowlisted keys `policyVersion` (`placement-v0.1`), `classId` (current primary A–F), `hasTrainingExperience` (boolean), `skip` (boolean), `equipment` (`barbell`/`pullUpBar` booleans), and `anchors` (at most three objects with `exerciseId`, `protocolVersion="strict-v1"`, `loadKg`, `reps`, `durationSeconds`). Normalize anchor order/default zero values before operation comparison; body mass, age and timezone come from server profile snapshots, never client-supplied level or XP. Validate numeric types/ranges with the existing profile/workout bounds plus the stricter v0.1 movement limits; reject unknown fields, duplicate IDs and wrong metrics. Never-trained/skip flows store no performance answers and cannot produce an elevated result.

1. Extend `initialize_user(p_profile jsonb)` with an optional `placement` object. Its existing parameters and legacy return keys remain compatible. On the first successful onboarding only, initialize the profile/classes as today, then register the versioned assessment or an explicit never-trained/skipped/ineligible/insufficient outcome in the **same transaction**. Existing onboarded users receive no automatic enrollment. Old clients omitting `placement` continue to work and get no placement row. A retry carrying an existing placement operation performs the operation lookup/normalized-request comparison first and returns its immutable submission result without resetting profile, XP or classes, even if confirmation or class switching has since occurred. Reusing that operation with changed assessment data rejects with `22023`.
2. `submit_placement_assessment_v1(p_operation_id uuid, p_request jsonb) RETURNS jsonb` is authenticated and owner-derived. It may create a new attempt only for an account enrolled during new onboarding, with initial `has_training_experience=true` and no confirmation. It cannot enroll a legacy account or replace a confirmed placement. Lock `users`, look up `(user_id, operation_id)`, compare the normalized original request and return its immutable first result **before** testing current class/status/eligibility. Only a new operation checks current class/policy/input validity, supersedes any pending attempt and stores a new provisional or ineligible/insufficient/skipped result. It writes no earned or confirmed progression.
3. `get_placement_state_v1() RETURNS jsonb` returns the authenticated owner's sanitized state/readiness projection and earned XP baseline deltas. An account with no row returns `status=unassessed` and no invented assessment. No other user ID argument is accepted.
4. A private reward-insert trigger records eligible evidence after a **new** `workout_rewards` insert inside `complete_workout`. It participates in the existing user lock and transaction, performs no external I/O and cannot be invoked by clients. A reward retry returns its immutable receipt and inserts no evidence again. Placement failure rolls back the transaction; it must never leave a rewarded workout with half-written evidence. Historic import remains excluded.

Onboarding UI must ask explicitly whether the user has trained before; current `beginner/intermediate/advanced` alone does not distinguish never-trained from a novice with practice. Never-trained forces 1/1 and no confirmation enrollment. Users can skip; missing/unsupported age/equipment reports remain usable for ordinary workouts and experience-sensitive plan choice. Missing backend RPC must never cause a client to fabricate confirmed placement or write a level.

Enrollment and confirmation eligibility are distinct. A never-trained initial row records the onboarding outcome but permanently disallows this initial experienced-placement path. For an initially experienced enrolled account with no confirmation, skipped/ineligible/insufficient/superseded attempts may be followed by a new explicit attempt; each snapshots the current profile age/body mass/timezone and rechecks coverage. Editing those fields alone never changes a prior result. Terminal confirmed state allows immutable-operation replay only, not a new placement. Old accounts without initial enrollment stay unassessed.

## 4. Confirmation evidence

- Consider only workouts first rewarded after the assessment, with `training_started_at >= assessment.submitted_at`, completed status, `is_imported=false`, non-suspicious receipt and the same current primary class. Exclude warm-up, incomplete and unsupported-mode sets; match exact canonical UUID/protocol. Barbell anchors require 4–10 reps; bodyweight anchors require no external load; forearm plank uses timed mode.
- Select the highest valid working-set score per distinct anchor in each session; calculate the class score using v0.1 median/lower-of-two and class/equipment caps. At least two valid anchors must be present in each qualifying session; one repeated anchor is insufficient.
- Require two qualifying sessions on two different local dates in the assessment's immutable timezone. Choose the first qualifying session in serialized reward-processing order, then the first subsequent qualifying session whose snapshot-local date differs. Same-day sessions are recorded but never replace the first score or satisfy the second date. The confirmed class floor is the **lower of those two session scores**, bounded by the v0.1 class cap. Map that result to global 1/3/5/7/10. A lower confirmed score is a correction of the provisional estimate, not a reduction of earned level.
- Confirmation may be higher or lower than the self-report; forged self-report alone never increases confirmed values. The confirmation is immutable and records the assessment/evidence/version. Other sessions still earn their ordinary XP/streak/quest rewards through the existing path.
- A primary-class change before confirmation supersedes the pending assessment; existing evidence is not transferred. A fresh explicit assessment may target the new class before any confirmation. After confirmation, class readiness applies only when its assessed class is primary. Switching back restores the same readiness record; P9 earned floors remain untouched. Secondary class gets no placement. Global readiness stays account-scoped after confirmation.

The lower-of-two confirmation rule and storage/API details above are new D-062 implementation-contract proposals, beyond the already approved seven threshold rows.

## 5. Progress after placement without awarding synthetic XP

A simple `max(earnedLevel, placementFloor)` would leave a level-10 placement visually stuck until earned XP catches up. The proposed readiness lane instead counts real XP earned **after confirmation** against the existing threshold differences. Capture earned global/class XP after the confirming workout's ordinary award for audit; that workout does not count twice toward readiness progress. Each later new reward receipt appends one `phase=progress` event from `result.earnedXP` and the matching `result.classResults[].xpEarned` (zero if absent). Never use cumulative `newTotalXP`, `current_xp` differences or `switch_class.xp_granted`. Calculate deltas by summing those events, not by comparing transaction-start timestamps. Class switching can reconstruct historical class XP and must not create readiness progress; only a subsequent new reward receipt can do so.

Global threshold to reach level `n`: `G(1)=0`; `G(n)=floor(100*(n-1)^1.5)` for 2–100. Class threshold: `C(1)=0`; `C(n)=floor(xp_base*n^xp_slope)` for 2–20, matching D-043/P9 with coefficients snapshotted at confirmation. For confirmed floor `f` and nonnegative receipt-backed XP delta `d`, readiness level is the greatest `n >= f` with `threshold(n)-threshold(f) <= d`, capped at 100/20; expose the greater of that result and the current earned/legacy level. XP-to-next is the remaining **difference**, not earned total subtracted from a placement threshold. When the earned lane is already higher, its existing XP-to-next calculation is used. No XP is credited to the ledger by these calculations.

Example: global floor 5 has `G(5)=800`; reaching readiness 6 requires `G(6)-G(5)=1118-800=318` genuine post-confirmation XP. Global earned level can remain below 5 during this period. Titles and unlocks continue following the earned lane. This offset progression is a new D-062 policy detail requiring explicit local approval.

## 6. Flutter and plan behavior

- New typed placement domain/repository/provider; plain immutable Dart models avoid unnecessary generated-code churn. Preview thresholds mirror SQL and are golden-tested against shared fixtures. PostgreSQL recalculates every stored value.
- New onboarding assessment step follows class/biometric input and precedes final confirmation. Three class-specific anchors with variant/unit labels, exact catalog resolution, skip path, VI/EN estimate text and no promise of earned XP. Draft stays owner-scoped and resets on logout/account switch. A stable operation ID survives retries of the same submission; changing normalized answers gets a new operation.
- Fix `beginnerProfileProvider` to use actual saved experience. Never-trained/beginner can use the existing first-week engine. Experienced users are routed to existing routine selection/editor with readiness context, without the hardcoded beginner plan or invented automatic loads. Generating new experienced prescriptions is P10.4 work, not an implicit change in this task.
- Readiness card uses explicit estimate/confirmed labels and a distinct progress lane. Existing earned progression models and receipt animations stay earned. Refresh placement after successful completion, onboarding and class change; generation fencing prevents an old account's response from appearing after switching accounts.

## 7. Internal pilot evaluation

Use privileged SQL aggregates over the owner-scoped ledger, not external analytics. The offer denominator is **completed onboardings that supplied the placement envelope**, not all screen impressions or abandoned onboardings; old clients without the object are unobserved. Count enrolled accounts and assessment attempts separately so retries/revisions do not inflate people counts. Count per-version/class submitted/skipped/ineligible/insufficient/confirmed; provisional/confirmed levels 1–5; upward/downward differences; server-timestamp duration and receipt-event sessions to confirmation. Persist the server recommendation `beginner_first_week`, `routine_selection` or `none` per attempt; report recommended plan routing, not an unmeasured actual navigation outcome. Report missingness. Age and body-mass band analysis uses stored snapshots. Gender/biological-sex collection or analysis is not authorized by this local schema decision.

Proposed small-cell rule: do not return a subgroup count or rate unless its denominator is at least 20; display `insufficient_sample` instead. Review at each explicitly authorized pilot checkpoint; no automatic significance or fairness PASS from reaching a sample size. Broad rollout requires an owner-reviewed report and explicit decision to keep, revise/version or stop the calibration. No pilot collection or production activation occurs during local implementation.

## 8. Acceptance and recovery

Local acceptance requires SQL/RLS/ACL tests, real two-connection retry/completion tests, Dart parity/edge cases, onboarding/state-isolation and VI/EN UI tests. Legacy history/XP/rewards/150 curated UUIDs remain byte/value-equivalent. Test class changes, altered body-mass profiles, insufficient/duplicate anchors, NULL/nonfinite/extreme inputs, suspicious/imported/old workouts, same-day evidence, both confirmation directions, account deletion, failure rollback, retry and cross-account isolation. Add explicit regression proving global readiness 10 grants no level-10 title now or on the next workout.

Recovery uses an additive correction and disabled placement UI/registration, preserving earned rows and evidence. Do not delete confirmations, rewrite awards, repair production history or weaken RLS. Production P10.1 gates remain independent.
