**Goal:** Add provisional onboarding placement and receipt-backed confirmation with a separate readiness progression lane.
**Architecture:** Flutter previews the approved `placement-v0.1` table; PostgreSQL validates/persists assessments and derives confirmation inside the existing completion transaction. Separate readiness state prevents earned progression and rewards from consuming a placement floor.
**Tech Stack:** Flutter/Dart, Riverpod, existing Supabase/PostgreSQL, Node isolated SQL/concurrency harness. No new dependency.
**Spec:** `docs/planning/P10_3B_PLACEMENT_CONTRACT.md`; numeric policy in `docs/planning/P10_3A_PLACEMENT_THRESHOLDS_V0_1.md`.

## Review focus

- Lost submission responses retried after confirmation/class change must return the same immutable receipt; changed payload must reject.
- Class switching reconstructs XP historically; only new reward-receipt deltas can advance readiness.
- An old account or a new never-trained account cannot enroll through a later direct RPC.
- Wrong exercise variants, weighted bodyweight, insufficient anchors and same-day sessions cannot confirm placement.
- Local readiness global 10 must never produce an earned level-10 unlock now or after later workouts.
